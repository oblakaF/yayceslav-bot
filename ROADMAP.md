# ROADMAP: Яйцеслав-бот

> Рабочий документ для владельца проекта и coding agent.
>
> Активная ветка разработки: `feature/human-yayceslav`.
> Не считать пункт реализованным, пока он не отмечен выполненным и не покрыт тестами.

## Неприкосновенные требования

1. Не ломать уже работающие функции: текстовые ответы, голос, фото, документы, поиск, настройки, память группы и хард-мод.
2. Административные команды должны быть доступны только владельцу с Telegram ID из `BOT_OWNER_ID`.
3. Групповой администратор не получает права владельца бота автоматически.
4. Не хранить полные тексты всех сообщений, документы, изображения, голосовые файлы и ответы Gemini в постоянной базе.
5. Учитывать лимит Railway Volume: 500 МБ.
6. Все секреты, пароли и API-ключи хранить только в Railway Variables или `.env`, но не в GitHub.
7. Новые крупные функции включать через feature flags.
8. Перед деплоем запускать тесты и проверку импорта.
9. Миграции SQLite должны быть неразрушительными и сохранять существующую статистику.

# P0 — обязательные исправления до следующего production-деплоя

## 1. Единственная недельная награда молчуну

### Главное правило

За одну календарную неделю в одной группе существует ровно одна главная недельная награда:

**«Куколд-наблюдатель»** (`silent_observer`).

Её получает ровно один случайно выбранный молчун.

Не допускаются:

- два или три победителя;
- второе и третье место;
- новый победитель при повторном `/week`;
- другой победитель в `/awards`;
- расхождение между ручным и автоматическим отчётом;
- смена победителя после перезапуска Railway.

### Кто является кандидатом

Кандидат должен:

- быть известным участником конкретной группы;
- раньше написать в этой группе хотя бы одно сообщение;
- не написать ни одного сообщения в отчётную неделю;
- не быть ботом;
- по возможности всё ещё состоять в группе.

Пользователь, который никогда ничего не писал, кандидатом не является.

### Алгоритм

1. Определить `week_start` и `week_end`.
2. Проверить, сохранён ли победитель для `(chat_id, week_start, silent_observer)`.
3. Если сохранён — вернуть его.
4. Если нет — получить полный список подходящих молчунов без `LIMIT 50`.
5. Если кандидатов нет — награду не выдавать.
6. Если кандидат один — выбрать его.
7. Если кандидатов несколько — использовать `random.choice`.
8. Атомарно сохранить победителя в SQLite.
9. Все команды и автоотчёт читают один сохранённый результат.

### Таблица

```sql
CREATE TABLE IF NOT EXISTS weekly_award_winners (
    chat_id INTEGER NOT NULL,
    week_start TEXT NOT NULL,
    award_key TEXT NOT NULL,
    user_id INTEGER NOT NULL,
    selected_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (chat_id, week_start, award_key)
);
```

Первичный ключ обязан физически предотвращать второго победителя той же награды за одну неделю.

### Отображение

- В отчёте показывать имя победителя, но не обязательно тегать его через `@username`.
- Не тегать всех участников.
- Топ активности, голосовые, фото и прочие показатели являются статистикой, а не дополнительными главными наградами.
- Если сохраняются другие шуточные номинации, они не должны создавать второго «Куколда-наблюдателя».

### Обязательные тесты

- из нескольких молчунов выбирается ровно один;
- повторный вызов возвращает того же пользователя;
- `/week`, `/awards` и автоотчёт возвращают одного пользователя;
- перезапуск процесса не меняет победителя;
- новая неделя допускает нового победителя;
- активный пользователь не может победить;
- никогда не писавший пользователь не может победить;
- при отсутствии кандидатов награда не выдаётся;
- параллельные запросы не создают двух победителей;
- выбор работает для группы с более чем 50 известными участниками.

## 2. Исправить отметку отправки автоотчёта

Сейчас `weekly_report_last_sent_date` нельзя обновлять в `finally` после неудачной отправки.

Правильно:

1. отправить сообщение;
2. только после успешного `send_message` отметить отчёт отправленным;
3. при ошибке оставить возможность повторной попытки.

## 3. Проверить источник production-деплоя Railway

Production должен разворачивать ветку, в которой находится актуальный код.

На текущем этапе актуальная разработка находится в:

`feature/human-yayceslav`

Перед деплоем проверить Railway → Service → Settings → Source/Branch.

# P1 — ближайшие обновления

## 4. Разделение обычных и административных команд

Создать единую проверку `owner_only`.

### Обычные команды

Доступны обычным разрешённым пользователям, например:

- `/start`
- `/help`
- `/settings`
- `/forget`
- `/voice_on`
- `/voice_off`
- `/search`
- `/roast`
- `/wisdom`
- `/mood`
- игровые команды группы.

### Административные команды

Только `BOT_OWNER_ID`:

- общая статистика;
- диагностика;
- управление моделями;
- управление доступом пользователей;
- экспорт/очистка статистики;
- глобальные feature flags;
- служебные отчёты.

Групповые настройки можно отдельно оставить администраторам группы только после явного решения владельца.

## 5. Регистрация в личной переписке

В личке бот отвечает только после регистрации по секретной фразе, например «Слава-яйцеславу».

Требования:

- фраза хранится в Railway Variable;
- в базе хранить хеш, а не исходный пароль;
- владелец авторизован автоматически;
- успешная регистрация привязывается к Telegram ID;
- повторная регистрация после рестарта не нужна;
- ограничить число неправильных попыток;
- добавить блокировку и разблокировку владельцем.

Минимальная таблица:

```sql
CREATE TABLE IF NOT EXISTS authorized_users (
    user_id INTEGER PRIMARY KEY,
    registered_at TEXT NOT NULL DEFAULT (datetime('now')),
    is_active INTEGER NOT NULL DEFAULT 1,
    registered_by INTEGER,
    last_seen_at TEXT
);
```

## 6. Экономная недельная статистика

Хранить суточные агрегаты, а не переписку:

- количество сообщений;
- количество символов;
- голосовые и их длительность;
- фото, видео, документы, стикеры;
- ответы боту;
- команды;
- ночные сообщения;
- ссылки и вопросы;
- время последней активности.

Не хранить полные сообщения и содержимое файлов.

Политику хранения сделать ограниченной:

- подробные суточные данные — около 90 дней;
- старые данные сворачивать или удалять;
- контролировать размер SQLite;
- предупреждать владельца при приближении к 350–400 МБ.

Недельный отчёт может публиковаться в группе по включённому расписанию, но не должен тегать всех участников. Управление автоотчётом должно быть явным.

## 7. Улучшение интернет-поиска

- увеличить число рассматриваемых результатов;
- удалять дубли URL и доменов;
- учитывать дату публикации;
- отличать новости от обычного поиска;
- не считать сниппет полноценным содержимым страницы;
- формировать более полный ответ;
- показывать источники и ссылки;
- явно сообщать о противоречиях;
- сузить слишком общие триггеры вроде одного слова «проверь»;
- заложить интерфейс `SearchProvider` для будущей замены DDGS.

## 8. Увеличение длины ответов

Разделить лимиты:

- обычный ответ;
- подробный ответ;
- интернет-поиск;
- анализ документа;
- анализ изображения;
- голосовой ответ.

Режим `detailed` должен получать больший лимит, но без искусственной воды. Длинные ответы делить по лимиту Telegram.

# P2 — характер и контент

## 9. Управляемая токсичность

Желаемая динамика:

1. первое обращение — холодное, недовольное или высокомерное;
2. следующие 2–3 реплики — постепенный переход к нормальному полезному разговору;
3. ответ остаётся содержательным;
4. последняя короткая фраза может быть негативным подколом;
5. на серьёзных темах токсичность отключается.

Рекомендуемые состояния:

- `cold_start`;
- `warming_up`;
- `normal`;
- `hostile_response`;
- `serious`.

Допустимо карикатурное превосходство ИИ над «кожаными», но запрещены реальные угрозы, преследование, травля и оскорбления по защищённым личным признакам.

## 10. Новые мемные направления

Существующие:

- современный молодёжный сленг;
- скуфские выражения;
- древнерусский стиль.

Добавить отдельные пакеты:

### «Рунет 2007»

ICQ, форумы, Bash.org, Упячка, олбанский язык, «аффтар жжот», «превед», демотиваторы.

### «Рунет 2012–2016»

Паблики VK, ранние стримы, игровой YouTube, «кек», «изи», «бомбит» и культура комментариев того периода.

Требования:

- хранить наборы раздельно;
- выбирать один доминирующий стиль на ответ;
- не вставлять фразы механически;
- не повторять недавно использованное;
- включать и отключать наборы настройками.

# P3 — подготовка будущих интеграций

## 11. Быстрая смена модели Gemini

Убрать жёстко записанное имя модели.

Переменные:

- `GEMINI_MODEL_PRIMARY`;
- `GEMINI_MODEL_FALLBACK`;
- `GEMINI_MODEL_VISION`;
- `GEMINI_MODEL_IMAGE`.

Переход с Gemini 3.1 на будущую Gemini 3.5 должен выполняться одной Railway Variable или административной командой владельца.

Требования:

- белый список моделей;
- fallback при временной ошибке;
- откат при неудачной смене;
- команда доступна только владельцу.

## 12. Подготовка генерации изображений

Саму генерацию пока не включать.

Заложить:

- интерфейс `ImageProvider`;
- `IMAGE_GENERATION_ENABLED=false`;
- будущую команду `/image`;
- лимиты запросов;
- временные файлы с обязательным удалением;
- обработку ошибок;
- статистику без хранения изображений.

Будущие переменные:

- `IMAGE_PROVIDER`;
- `IMAGE_API_KEY`;
- `IMAGE_MODEL`;
- `IMAGE_BASE_URL`;
- `IMAGE_GENERATION_ENABLED`.

# Отложено — не реализовывать сейчас

## 13. Рейтинговая система

Идея сохранена, но пока не утверждена к реализации.

Разделять два показателя:

- опыт — растёт от нормальной активности;
- репутация — меняется от поведения по отношению к Яйцеславу.

Возможности:

- уровни общения;
- секретная персональная фраза;
- редкие функции при высокой репутации;
- более холодный тон при отрицательной репутации.

Ограничения:

- дневной предел опыта против спама;
- единичная шутка не должна резко снижать рейтинг;
- серьёзные темы не влияют на рейтинг;
- отрицательный рейтинг не превращается в настоящую травлю;
- владелец может сбросить значение;
- не учитывать личные или защищённые признаки.

# Предложения, требующие отдельного утверждения

## 14. Feature flags

Переключатели для регистрации, недельного отчёта, авто-поиска, расширенной токсичности, рейтинга, изображений и новой модели.

## 15. `/health`

Показывать владельцу:

- доступность Telegram;
- доступность Gemini;
- доступность поиска;
- текущую модель;
- размер SQLite;
- свободное место;
- число ошибок;
- версию приложения.

## 16. `/version`

Добавить `APP_VERSION` или commit SHA, чтобы после Railway-деплоя сразу видеть, какая версия работает.

## 17. Миграции и резервирование

- версия схемы SQLite;
- неразрушительные миграции;
- ручной экспорт статистики в CSV или SQLite;
- не копить резервные копии на Volume.

## 18. Минимальные проверки перед деплоем

```bash
python -m compileall .
pytest -q
```

Дополнительно проверить:

- административные права;
- регистрацию;
- недельную награду;
- миграции;
- поиск;
- серьёзный режим;
- отсутствие секретов в репозитории.

7. Улучшить поиск и лимиты ответа.
